## 1. OpenID4VCI 1.0 の Credential Issuer メタデータ {#oid4vci-metadata}

テナントの認可サーバー設定の `credential_issuer_metadata` を、OpenID4VCI 1.0 Final（Section 12.2.4）の形で読む。

```json
"credential_issuer_metadata": {
  "credential_endpoint": "https://idp.example.com/{tenant-id}/v1/credentials",
  "nonce_endpoint": "https://idp.example.com/{tenant-id}/v1/credentials/nonce",
  "credential_configurations_supported": {
    "identity_credential": { "format": "dc+sd-jwt", "scope": "identity_credential", "vct": "..." }
  }
}
```

- `credential_issuer` を省略すると、認可サーバーの `issuer` を使う。`authorization_servers` は出さない（Credential Issuer が認可サーバーを兼ねる）
- `credential_configurations_supported` が空のテナントは Credential Issuer ではなく、メタデータは `404`

### 1.1 旧ドラフトの設定 {#oid4vci-draft-metadata}

旧ドラフトの形（`credentials_supported` の配列、`batch_credential_endpoint` など）で書かれた設定は、エラーにはならず**無視される**。VC の発行はこれまで HTTP に公開されていなかったため、動いていた機能が止まることはない。

旧形式の値は管理 API の GET に出ない（従来も出していなかった）ため、GET → 編集 → PUT で消える。1.0 の形の値は GET に出て、往復で保たれる。VC を発行するなら 1.0 の形で書き直す。

### 1.2 well-known のパス {#oid4vci-well-known}

Credential Issuer Identifier（= `https://host/{tenant-id}`）にパスがあるため、仕様どおり well-known をホストとパスの間に挟む。

| 文書 | パス |
|---|---|
| Credential Issuer メタデータ（OpenID4VCI 1.0 Section 12.2.2）| `/.well-known/openid-credential-issuer/{tenant-id}` |
| 認可サーバーメタデータ（RFC 8414 Section 3.1）| `/.well-known/oauth-authorization-server/{tenant-id}`（中身は `/{tenant-id}/.well-known/openid-configuration` と同じ）|
