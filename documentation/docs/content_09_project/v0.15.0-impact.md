## 1. 外向きのクライアント認証に client_secret_jwt / private_key_jwt を追加 {#outbound-client-assertion}

**🟢 追加 / 🔴 破壊的。** idp-server が外部のトークンエンドポイントを呼ぶとき（Federation のコード交換、`http_request` の `oauth_authorization` でのトークン取得）のクライアント認証に、`client_secret_jwt` と `private_key_jwt`（RFC 7523 のクライアントアサーション）を追加した。

### 1.1 設定 {#outbound-client-assertion-config}

`client_authentication_type` に方式を書き、`client_secret_jwt` / `private_key_jwt` の追加の値を `client_authentication` に書く。Federation の `payload` と `oauth_authorization` で同じ形。

| `client_authentication_type` | 送るもの |
|---|---|
| `client_secret_basic` | `Authorization: Basic` ヘッダー |
| `client_secret_post` | フォームの `client_secret` |
| `client_secret_jwt` | `client_secret` で署名したクライアントアサーション |
| `private_key_jwt` | `client_authentication.signing_key` で署名したクライアントアサーション |
| `none` | `client_id` だけ |

省略したときは従来どおり。Federation は `client_secret_post`、`oauth_authorization` は `client_id` だけ。

| `client_authentication` のキー | 内容 | 省略時 |
|---|---|---|
| `signing_algorithm` | `client_secret_jwt` は `HS256` / `HS384` / `HS512`、`private_key_jwt` は `RS256` / `PS256` / `ES256` など | `client_secret_jwt` は `HS256`、`private_key_jwt` は `signing_key` の `alg` |
| `signing_key` | `private_key_jwt` の秘密鍵を含む JWK 1 つ | なし（`private_key_jwt` では必須） |
| `assertion_audience` | `token_endpoint` / `issuer` | `token_endpoint` |
| `issuer` | `assertion_audience: issuer` のときの宛先。Federation は `payload` の `issuer` を使うので不要 | なし |

アサーションは `iss` = `sub` = `client_id`、`jti` は毎回新しい値、有効期間 60 秒。`client_secret_jwt` の `HS256` には 32 バイト以上の `client_secret` が要る（`HS384` は 48、`HS512` は 64）。

### 1.2 知らない client_authentication_type をエラーにする {#outbound-client-authentication-unknown-type}

`client_authentication_type` に上の 5 つ以外の値があると、トークン要求のときにエラーにする（Federation はコールバックが失敗し、`oauth_authorization` は外部 API の呼び出しが失敗する）。これまでは黙って、Federation は `client_secret_post`、`oauth_authorization` は `client_id` だけで送っていたため、`private_key_jwt` と書いても効いていないことに気づけなかった。

更新の前に、保存済みの設定に知らない値が無いかを確かめる（PostgreSQL）。

```sql
SELECT 'federation_configurations' AS source, id
  FROM federation_configurations
 WHERE jsonb_path_exists(payload, 'lax $.**.client_authentication_type ? (!(@ == "client_secret_basic" || @ == "client_secret_post" || @ == "client_secret_jwt" || @ == "private_key_jwt" || @ == "none" || @ == ""))')
UNION ALL
SELECT 'authentication_configuration', id
  FROM authentication_configuration
 WHERE jsonb_path_exists(payload, 'lax $.**.client_authentication_type ? (!(@ == "client_secret_basic" || @ == "client_secret_post" || @ == "client_secret_jwt" || @ == "private_key_jwt" || @ == "none" || @ == ""))')
UNION ALL
SELECT 'identity_verification_configuration', id
  FROM identity_verification_configuration
 WHERE jsonb_path_exists(payload, 'lax $.**.client_authentication_type ? (!(@ == "client_secret_basic" || @ == "client_secret_post" || @ == "client_secret_jwt" || @ == "private_key_jwt" || @ == "none" || @ == ""))')
UNION ALL
SELECT 'security_event_hook_configurations', id
  FROM security_event_hook_configurations
 WHERE jsonb_path_exists(payload, 'lax $.**.client_authentication_type ? (!(@ == "client_secret_basic" || @ == "client_secret_post" || @ == "client_secret_jwt" || @ == "private_key_jwt" || @ == "none" || @ == ""))');
```

見つかった設定は、これまでの動きに合わせて `client_secret_post`（Federation）か `none`（`oauth_authorization`）に直す。

### 1.3 password グラントの client_secret_basic {#outbound-client-authentication-password-basic}

`oauth_authorization` の `type: password` で `client_authentication_type: client_secret_basic` のとき、これまでは `Authorization` ヘッダーを付けず、シークレットも送っていなかった（`client_id` だけ）。今は `Authorization: Basic` ヘッダーを付ける。外部の認可サーバーがシークレット無しで受け付けていた構成では、送るシークレットが正しいかを確かめる。

### 1.4 まだ無いもの {#outbound-client-assertion-not-yet}

- 設定の登録・更新のときの `client_authentication_type` の確認（今はトークン要求のときにエラーになる）
- 管理 API の応答で `client_authentication.signing_key` を伏せること
