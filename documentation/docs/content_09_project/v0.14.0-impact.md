## 1. 管理APIのユーザー検索で `preferred_username` が完全一致になった（Issue #1866 / PR #1867） {#preferred-username-exact-match}

ユーザー一覧API（`GET .../users`）の `preferred_username` は**前後ワイルドカードの部分一致**でした。本バージョンから**完全一致**になります。

| | Before | After |
|---|---|---|
| 照合 | 部分一致（大文字小文字区別なし）| **完全一致** |
| `?preferred_username=ichiro` | `ichiro-ito` も `ito.ichiro` もヒット | **ヒットしない** |
| `?preferred_username=ichiro-ito` | ヒット | ヒット |
| `?preferred_username_like=ichiro` | （パラメータ自体が無い）| **ヒットする**（従来の挙動と同一）|

### 1.1 影響（🔴 破壊的）

**部分一致で呼んでいる管理画面・自動化は結果が変わります。** エラーにはならず、**0 件が返る**形で現れます。

`preferred_username` はテナントとプロバイダーの範囲で一意な識別子（`uk_preferred_username`）で、部分一致で探す対象ではありません。同じクラスの値は元から完全一致でした。

| 値 | 照合 |
|---|---|
| `email` / `phone_number` / `external_user_id` / `user_id` | 元から完全一致 |
| `preferred_username` | **部分一致だった（本変更で完全一致へ）** |
| `name` / `given_name` / `family_name` / `middle_name` / `nickname` | 部分一致のまま（**変更なし**）|
| `role` / `permission` | 部分一致のまま（**変更なし**）|

認証時の引き当て（`findByPreferredUsername`）は元から完全一致で、検索だけが例外になっていました。

### 1.2 移行手順

**部分一致が必要なら `preferred_username_like` へ送り先を変えてください。** 挙動は従来の `preferred_username` と同一（前後ワイルドカード・大文字小文字区別なし）です。

```diff
- GET .../users?preferred_username=ichiro
+ GET .../users?preferred_username_like=ichiro
```

管理画面が検索ボックスの入力をそのまま送っている場合、**送り先のパラメータ名を変えるだけで運用者の体験は変わりません**。

そのうえで、識別子として完全な値で引く呼び出し（自動化・API 直叩き）は `preferred_username` を使ってください。一意キーが効くため桁違いに速くなります。

人名で探す用途であれば `name` / `given_name` / `family_name` / `nickname` も部分一致のままです。

:::warning `preferred_username_like` は速くなりません
一意キーに対する前後ワイルドカードの部分一致は索引が効かず、テナントの全ユーザーを評価します。これは従来と同じコストです。**名前を分けた目的は、遅い経路を明示的な選択にすること**であって、部分一致自体を速くするものではありません。
:::

### 1.3 変わらないもの

- **他の検索パラメータの照合方式**。上の表のとおり、変更したのは `preferred_username` のみです
- **DB マイグレーション**。索引の追加もありません。既存の `uk_preferred_username` がそのまま効きます
- **レスポンスの形**。`list` / `total_count` / `limit` / `offset` は同じです
- **部分一致そのものの挙動**。`preferred_username_like` は従来の `preferred_username` と同じ照合をします

### 1.4 なぜ変えたか

100 万行・平均行幅 1058 bytes・heap 1121MB での実測（`performance-test/db-bench/bench_user_search.sh`）。

| クエリ | Before | After |
|---|---|---|
| COUNT | 337〜903 ms | **0.11 ms** |
| 一覧 | 828〜1229 ms | **0.08 ms** |

部分一致は前後ワイルドカードのため索引が原理的に効かず、ヒット件数に関係なくテナントの全行を評価していました。一覧APIは COUNT を先に実行してから一覧を引くため、1 回の検索でスキャンが 2 回走ります。

| ケース | テスト |
