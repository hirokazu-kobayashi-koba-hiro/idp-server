# v0.14.0 影響確認

本ドキュメントは **v0.14.0** に含まれる破壊的変更・挙動変更と、その**利用者側（RP / テナント運用者）への影響**をまとめる。

リリースに向けて対象変更が確定し次第、本ドキュメントへ追記していく。各変更は独立したセクション（`## N. <変更>`）として追加し、あわせて下記「影響まとめ」表に 1 行加える。

:::warning トリアージ未実施
本ドキュメントは作成したばかりで、**v0.13.0 以降のマージ全件はまだトリアージしていない**。現時点で登録されているのは下記セクションのみ。

洗い出しは `git log v0.13.0..main --merges`。v0.13.0 のときの進め方は [Issue #1797](https://github.com/hirokazu-kobayashi-koba-hiro/idp-server/issues/1797) を参照。

## 1. セルフサービス連絡先の確認・変更 {#self-service-contact}

認証済みエンドユーザーが自分の**メールアドレス**または**電話番号**を確認・変更する API を追加した（#1876 / Issue #1416）。

```
POST /{tenant-id}/v1/me/{email|phone}/verification            スコープ openid
POST /{tenant-id}/v1/me/{email|phone}/verification/{id}/verify スコープ openid
POST /{tenant-id}/v1/me/{email|phone}/change                   スコープ {channel}:change
POST /{tenant-id}/v1/me/{email|phone}/change/{id}/verify        スコープ {channel}:change
```

詳細は [セルフサービス 連絡先の確認・変更](../content_06_developer-guide/05-configuration/contact-verification.md)。

### 1.1 DBマイグレーション {#db-migration}

**⚙️ 全環境で必須。**

| ファイル | 内容 |
|---|---|
| `libs/idp-server-database/postgresql/V0_14_0_1__contact_verification_challenge.sql` | `contact_verification_challenge` テーブル + index 2 本 + RLS |
| `libs/idp-server-database/mysql/V0_14_0_1__contact_verification_challenge.mysql.sql` | 同（MySQL に RLS は無いため `tenant_id` 述語のみ）|

新規テーブルの追加のみで、既存テーブルへの変更は無い。

### 1.2 変更用スコープ {#change-scope}

**🔒 要点検。** 確認（`/verification`）は `openid` で足りるが、**変更（`/change`）は専用スコープを要求する**。

```json
"scopes_supported": ["openid", "profile", "email", "email:change", "phone:change"]
```

テナントの `scopes_supported` とクライアントの `scope` の**両方**に追加する必要がある。クライアント登録スコープの allow-list フィルタが効くため、片方だけではトークンに載らず、変更エンドポイントが常に `403 insufficient_scope` になる（fail closed）。

分離した理由は、確認と変更で動くものが違うため。

| | 確認 | 変更 |
|---|---|---|
| 変わるもの | `*_verified` のみ | 値 +`*_verified`（+ 対応する identity policy なら `preferred_username`）|
| 送信先 | 現在値に**固定** | リクエストの `new_value` |

変更を `openid` で通すと、**第三者クライアントに発行した通常の OIDC トークンにも識別子の移動能力を与える**ことになる。

### 1.3 管理権限 {#admin-permission}

**🔒 要点検。** サポート照会用の管理API に `idp:contact-verification-challenge:read` を新設した。

```
GET /v1/management/tenants/{tenant-id}/contact-verification-challenges
GET /v1/management/tenants/{tenant-id}/contact-verification-challenges/{id}
GET /v1/management/organizations/{org-id}/tenants/{tenant-id}/contact-verification-challenges
GET /v1/management/organizations/{org-id}/tenants/{tenant-id}/contact-verification-challenges/{id}
```

権限照合は `PermissionMatcher` のワイルドカード方式なので、**`idp:*` を持つロール（既定の `administrator`）は自動的に含む**。影響を受けるのは権限を明示列挙しているロールだけで、その場合は追加が必要。

### 1.4 管理APIが有効な検証コードを返す {#management-verification-code}

**🔒 要点検。**

```json
{ "target_value": "...", "delivery": "internal", "verification_code": "123456", "attempts": 0, "expired": false }
```

「コードが届かない」という問い合わせに答えるための API なので、**実際の送信先と有効なコード**を返す。チャレンジの消費には本人のアクセストークンが要るため、コードだけを入手したオペレーターが単独で確定させることはできない。

監査ログは永続なので、`after` ペイロードからは `verification_code` と `external_reference` を落としている。

委譲構成（外部サービスがコードを生成する場合）は `delivery: "external"` になり、`verification_code` の代わりに `external_reference` を返す。

### 1.5 セキュリティイベント型の追加 {#security-events}

**🟢 追加。** 16 種増えた。

```
{email,phone}_{verify,change}_request_{success,failure}
{email,phone}_{verify,change}_{success,failure}
```

ログイン時の `email_verification_*` とは別物で、こちらは**意図的なプロフィール操作**を記録する。確認と変更を分けてあるのは、変更だけがログイン識別子を動かすため。

フック / SIEM 側でイベント型を allow-list している場合は追加が必要。

### 1.6 テナント設定に `contact_change_policy` が増えた {#contact-change-policy}

**🟡 挙動変更。** `identity_policy_config` に `contact_change_policy` が加わり、**テナント取得のレスポンスに常に含まれる**（未設定でも既定値が出る）。

```json
"identity_policy_config": {
  "identity_unique_key_type": "EMAIL_OR_EXTERNAL_USER_ID",
  "contact_change_policy": {
    "identifier_move": { "allowed": true, "notify_previous_value": true },
    "attribute_only":  { "allowed": true, "notify_previous_value": true }
  }
}
```

影響するのは 2 パターン。

- テナント設定のレスポンスを**厳密なスキーマで検証**している自動化 → 未知キーで落ちる可能性
- **GET → 編集 → PUT** を自分で書いている運用 → 既定値がそのまま保存されるようになる

既定で効くのは `notify_previous_value: true` のみで、**変更の重さは既定では規定されない**（スコープだけが門番）。識別子が動くテナントは `authentication_conditions` / `max_auth_age_seconds` を明示的に書くことを推奨する。

`allowed` が掛かるのは**変更だけ**で、確認（`/verification`）には掛からない。確認は値を置き換えず `*_verified` を立てるだけのため。`authentication_conditions` / `max_auth_age_seconds` は確認にも掛かる。

### 1.7 `delete-expired-data` の内訳 {#delete-expired-data}

**🟡 挙動変更。** `POST /v1/admin/operations/delete-expired-data` のレスポンスに `contact_verification_challenge` が加わった。

```json
{ "deleted": { "...": 0, "contact_verification_challenge": 47 }, "total_deleted": 47 }
```

期限切れチャレンジは他の有効期限付き 7 テーブルと同じ入口で回収される。件数を固定長で扱っている自動化は影響を受ける。

### 1.8 既存の認証設定への影響 {#authn-config}

**影響なし。** 送信には既存の `type: "email"` / `type: "sms"` 認証設定をそのまま流用するが、

- 追加した `resend_cooldown_seconds` を読むのはセルフサービス側だけで、ログイン OTP 側は `retry_count_limitation` / `expire_seconds` しか読まない
- `templates` の `{email,phone}_{verify,change}` / `*_notice` は**未定義ならそれぞれの既定にフォールバック**するため、既存テンプレートの変更は不要（ただし `*_notice` だけは**フォールバックせずスキップ**する。[理由](../content_06_developer-guide/05-configuration/contact-verification.md)）
- `details` は生の `Map` のまま往復するため、保存済み設定に影響しない

認証ポリシー（`flow` 設定）の追加も不要。

## 2. 組織配下の認証設定 API の権限を修正 {#org-authentication-config-permission}

**🔴 破壊的変更。** 組織配下の認証設定 API が、認証**ポリシー**の権限で守られていた（Issue #1898）。

```
/v1/management/organizations/{organization-id}/tenants/{tenant-id}/authentication-configurations
```

| | 修正前 | 修正後 |
|---|---|---|
| 組織配下 | `idp:authentication-policy-config:{create,read,update,delete}` | `idp:authentication-config:{create,read,update,delete}` |
| システム管理用 | `idp:authentication-config:*` | （変更なし）|

同じリソースを扱う 2 本の API で要求する権限が食い違っていた。組織パスから来たというだけで、認証設定が持つもの（外部認証サービスの接続先と資格情報を含む）は変わらない。

### 2.1 影響を受けるロール {#affected-roles}

`idp:*` を持つロール（既定の `administrator`）は影響を受けない。権限を個別に列挙しているロールだけが対象。

| そのロールが持つ権限 | 修正前 | 修正後 |
|---|---|---|
| `idp:authentication-config:*` のみ | 組織配下を操作**できなかった**（403）| 操作できる |
| `idp:authentication-policy-config:*` のみ | 認証ポリシーに加えて**認証設定も操作できた** | 認証設定は 403 |

後者は権限の昇格にあたるため、**修正後に 403 になるロールがあっても、それが本来の状態**である。アップグレード前に、認証ポリシー権限だけで組織配下の認証設定を操作している運用がないか確認すること。必要なら `idp:authentication-config:*` を明示的に付与する。

### 2.2 ダッシュボードとの整合 {#dashboard}

idp-server-dashboard は認証設定の画面を `idp:authentication-config:read` で出し分けている。この修正で、画面の出し分けとサーバーの判定が一致する。

## 3. 本人確認設定の往復と `type` / `enabled` {#identity-verification-config}

本人確認設定（`identity-verification-configurations`）の管理 API で、GET が保存内容の一部を返さず、GET → 編集 → PUT で設定が消えていた（Issue #1900）。あわせて PUT の `type` と `enabled` の扱いを直した。システム管理用・組織配下の両方が対象。

### 3.1 GET が返す項目が増えた {#roundtrip}

**🟡 挙動変更。** DB には保存されていたが GET が返していなかった項目を返すようにした。

| 項目 | 修正前 | 修正後 |
|---|---|---|
| `result` | `verified_claims_mapping_rules` が空だと**キーごと無し** | 何か設定されていれば返る |
| `registration.response` | **常に無し** | 返る |
| `registration.basic_auth` | 常に `{}` | `username` / `password` を返す |

`result` が落ちていたのは、出力条件が `verified_claims_mapping_rules` の有無だけを見ていたため。`user_status` / `user_claims_mapping_rules` / `custom_properties_mapping_rules` / 各 `*_update_policy` しか持たない設定は、保存されていても一度も返らなかった。

GET のレスポンスにキーが増えるため、**厳密なスキーマで検証している自動化**は影響を受ける。

### 3.2 PUT の `type` が変更不可になった {#type-immutable}

**🔴 破壊的変更。**

```
PUT ... {"type": "<保存済みと違う値>"}   → 400 type cannot be changed
PUT ... {}  (type 省略)                 → 400 type is required
```

修正前は **200 が返るのに何も更新されなかった**。UPDATE 文が `WHERE id = ? AND type = ? AND tenant_id = ?` でリクエスト由来の新しい `type` を条件に使うため 0 行更新になり、それでもレスポンスは変更後の姿を返していたので、呼び出し側から成功と区別がつかなかった。

リネームを通す方向にはしていない。`type` は実行時に設定を引く際のキーであり、`identity_verification_application.verification_type` が記録している値でもあるため、変えると旧名で積まれた申込みが宙に浮く。

**PUT に毎回新しい `type` を入れている自動化は 400 になる。** GET の結果をそのまま PUT する使い方なら影響はない。

### 3.3 `enabled` が効くようになった {#enabled}

**🔴 破壊的変更。** ペイロードの `enabled` を DB のカラムに書くようにした。

修正前は INSERT / UPDATE ともカラムに触れておらず、DDL の `DEFAULT TRUE` のままだった。実行時の取得は `AND enabled = true` でカラムを見るため、`enabled: false` を書いても**設定は有効なままだった**。

既定は `true`（リクエスト・ドメインオブジェクトの両方）なので、`enabled` を書いていない設定は影響を受けない。**`enabled: false` を明示している設定は、アップグレード後に実際へ無効化される。**

無効化されるのが意図どおりか、アップグレード前に確認すること。

```sql
SELECT tenant_id, type FROM identity_verification_configuration WHERE payload->>'enabled' = 'false';
```

既存行のカラム値は移行しない。次にその設定を PUT したときにペイロードの値がカラムへ反映される。

## 4. 管理APIのユーザー検索で `preferred_username` が完全一致になった（Issue #1866 / PR #1867） {#preferred-username-exact-match}

ユーザー一覧API（`GET .../users`）の `preferred_username` は**前後ワイルドカードの部分一致**でした。本バージョンから**完全一致**になります。

| | Before | After |
|---|---|---|
| 照合 | 部分一致（大文字小文字区別なし）| **完全一致** |
| `?preferred_username=ichiro` | `ichiro-ito` も `ito.ichiro` もヒット | **ヒットしない** |
| `?preferred_username=ichiro-ito` | ヒット | ヒット |
| `?preferred_username_like=ichiro` | （パラメータ自体が無い）| **ヒットする**（従来の挙動と同一）|

### 4.1 影響（🔴 破壊的）

**部分一致で呼んでいる管理画面・自動化は結果が変わります。** エラーにはならず、**0 件が返る**形で現れます。

`preferred_username` はテナントとプロバイダーの範囲で一意な識別子（`uk_preferred_username`）で、部分一致で探す対象ではありません。同じクラスの値は元から完全一致でした。

| 値 | 照合 |
|---|---|
| `email` / `phone_number` / `external_user_id` / `user_id` | 元から完全一致 |
| `preferred_username` | **部分一致だった（本変更で完全一致へ）** |
| `name` / `given_name` / `family_name` / `middle_name` / `nickname` | 部分一致のまま（**変更なし**）|
| `role` / `permission` | 部分一致のまま（**変更なし**）|

認証時の引き当て（`findByPreferredUsername`）は元から完全一致で、検索だけが例外になっていました。

**空の値にも注意してください。** `?preferred_username=`（値が空）は、従来は前後ワイルドカードで全件に一致していましたが、本バージョンからは空文字との完全一致になり **0 件**が返ります。検索フォームの全項目を空のまま送る管理画面は、未入力の項目を送らないようにしてください。空の値で 0 件になるのは、元から完全一致の `email` などと同じ挙動です。

### 4.2 移行手順

**部分一致が必要なら `preferred_username_like` へ送り先を変えてください。** 挙動は従来の `preferred_username` と同一（前後ワイルドカード・大文字小文字区別なし）です。

```diff
- GET .../users?preferred_username=ichiro
+ GET .../users?preferred_username_like=ichiro
```

管理画面が検索ボックスの入力をそのまま送っている場合、**送り先のパラメータ名を変えるだけで運用者の体験は変わりません**。

そのうえで、識別子として完全な値で引く呼び出し（自動化・API 直叩き）は `preferred_username` を使ってください。**`provider_id` もあわせて渡すと**一意キー `uk_preferred_username (tenant_id, provider_id, preferred_username)` が最後まで効き、桁違いに速くなります（[4.4](#preferred-username-why)）。

人名で探す用途であれば `name` / `given_name` / `family_name` / `nickname` も部分一致のままです。

:::warning `preferred_username_like` は速くなりません
一意キーに対する前後ワイルドカードの部分一致は索引が効かず、テナントの全ユーザーを評価します。これは従来と同じコストです。**名前を分けた目的は、遅い経路を明示的な選択にすること**であって、部分一致自体を速くするものではありません。
:::

### 4.3 変わらないもの

- **他の検索パラメータの照合方式**。上の表のとおり、変更したのは `preferred_username` のみです
- **DB マイグレーション**。索引の追加はありません。`provider_id` を渡さない完全一致は一意キーの先頭列（`tenant_id`）までしか絞れないため、`(tenant_id, preferred_username)` の索引を [Issue #1910](https://github.com/hirokazu-kobayashi-koba-hiro/idp-server/issues/1910) で追加する予定です
- **レスポンスの形**。`list` / `total_count` / `limit` / `offset` は同じです
- **部分一致そのものの挙動**。`preferred_username_like` は従来の `preferred_username` と同じ照合をします

### 4.4 なぜ変えたか {#preferred-username-why}

100 万行・平均行幅 1058 bytes・heap 1121MB での実測（`performance-test/db-bench/bench_user_search.sh`）。

| クエリ | Before（部分一致） | After（`provider_id` なし） | After（`provider_id` あり） |
|---|---|---|---|
| COUNT | 337〜903 ms | 28〜145 ms | **0.11 ms** |
| 一覧 | 828〜1229 ms | 35 ms | **0.08 ms** |

一意キーは `(tenant_id, provider_id, preferred_username)` の順で、PostgreSQL 15 は途中の列を飛ばして探索できません。そのため `provider_id` を渡さない完全一致は、索引上でテナントの全エントリを読みます（それでも部分一致より 1 桁速い）。`provider_id` なしでも一意キー並みに引けるよう、[Issue #1910](https://github.com/hirokazu-kobayashi-koba-hiro/idp-server/issues/1910) で索引を追加します。

部分一致は前後ワイルドカードのため索引が原理的に効かず、ヒット件数に関係なくテナントの全行を評価していました。一覧APIは COUNT を先に実行してから一覧を引くため、1 回の検索でスキャンが 2 回走ります。

### 4.5 動作確認

| ケース | テスト |
|---|---|
| 完全一致で当たる / 部分一致では当たらない | `e2e/.../organization/organization_user_search_preferred_username.test.js` |
| `preferred_username_like` が部分一致で当たる / 大文字小文字を区別しない | 同上 |

## 6. FAPI の redirect_uri 検証を `openid` なしのリクエストにも適用 {#fapi-redirect-uri}

**🔴 破壊的変更。** FAPI 1.0 Advanced と FAPI 2.0 Security Profile で、`openid` スコープを含まない認可リクエストにも redirect_uri の検証を適用するようにした（Issue #1902）。

FAPI 1.0 Baseline 5.2.2-8/9/10（Advanced が引き継ぐ）は、redirect_uri の必須・事前登録・登録値との完全一致を求めている。FAPI 2.0 は、必須を 5.3.2.2-6 で求め、事前登録と完全一致は OAuth 2.0 の登録（RFC 6749 3.1.2.3）と open redirector の禁止による。これまでは `openid` スコープを含むリクエスト（OIDC の検証経路）にだけ適用されていて、含まないリクエスト（JARM を使う Advanced、`openid` なしの FAPI 2.0 の PAR など）には適用されていなかった。FAPI 1.0 Baseline は以前から両方に適用している。

| | 修正前 | 修正後 |
|---|---|---|
| redirect_uri の省略 | 登録済みの先頭の URI を使う | エラー（`invalid_request`） |
| 未登録・登録値と異なる redirect_uri | 受理 | エラー（`invalid_request`） |
| エラーの返し方 | 一部のエラーは redirect_uri へリダイレクト | redirect_uri の検証エラーは認可サーバーのエラー画面（PAR は 400） |

### 6.1 影響を受ける構成 {#fapi-redirect-uri-affected}

`openid` スコープを含まない FAPI 1.0 Advanced / FAPI 2.0 のリクエストで、次のどちらかに当てはまるクライアント。

- redirect_uri を省略している（request object・PAR のパラメータに含めていない）
- 登録済みの redirect_uri と文字列が完全に一致しない値を送っている

`openid` スコープを含むリクエストは、以前から同じ検証を受けているため影響しない。

### 6.2 確認 {#fapi-redirect-uri-check}

| ケース | テスト |
|---|---|
| FAPI 2.0：`openid` なしの PAR で未登録・省略の redirect_uri を拒否、直接の認可リクエストのエラーを未登録の redirect_uri へ返さない | `e2e/src/tests/spec/fapi2_0_security_profile.test.js` |
| FAPI 1.0 Advanced：`openid` なし（JARM）で未登録・省略の redirect_uri を拒否、エラーを未登録の redirect_uri へ返さない | `e2e/src/tests/spec/fapi_advance.test.js` |

## 7. FAPI のクライアント認証の要件を PAR と refresh token にも適用 {#fapi-client-authentication}

**🔴 破壊的変更。** FAPI の各プロファイルのクライアント認証の要件を、認可コードのトークンリクエストだけでなく、クライアントが認証するすべてのリクエスト（PAR、refresh token）に適用するようにした（Issue #1902）。refresh token のリクエストのプロファイルは、更新する grant のスコープから決める。

| 要件 | FAPI 1.0 Baseline | FAPI 1.0 Advanced | FAPI 2.0 |
|---|---|---|---|
| 認証方式 | `client_secret_basic` / `client_secret_post` を拒否（5.2.2-4）| `client_secret_*` と public client を拒否（5.2.2-14/16）| `client_secret_*` と public client を拒否（5.3.2.1）|
| client assertion の署名アルゴリズム | ― | PS256 / ES256（8.6）| PS256/384/512・ES256/384/512・EdDSA（5.4.1）|
| 鍵長 | RSA 2048 bit・EC 160 bit 以上（5.2.2-5/6）| 同左 | RSA 2048 bit・EC 224 bit 以上（5.4.1）|
| `client_secret_jwt` の secret | HS256 は 32・HS384 は 48・HS512 は 64 octets 以上（5.2.2-3、OIDC 16.19）| ― | ― |
| client assertion の `aud` | ― | ― | issuer の文字列のみ（5.3.2.1-8）|
| DPoP proof の署名アルゴリズム | ― | ― | refresh token でも 5.4.1 のアルゴリズムに制限 |

| | 修正前 | 修正後 |
|---|---|---|
| 認可コードのトークンリクエスト | 検証 | 検証 |
| PAR | FAPI 2.0 の署名アルゴリズム・鍵長・`aud` のみ | すべて |
| refresh token | 検証なし | すべて |
| 満たさないときのエラー | 400（認証方式の制限は `unauthorized_client`、ほかは `invalid_client`）| `invalid_client`（RFC 6749 5.2）。トークンエンドポイントは 401、PAR はほかのクライアント認証の失敗と同じ 400 |

あわせて次を変更した。

- **`client_assertion_type`**：`private_key_jwt` / `client_secret_jwt` で、値が `urn:ietf:params:oauth:client-assertion-type:jwt-bearer`（RFC 7523 2.2）でなければ `invalid_client`（トークンエンドポイントは 401、PAR は 400）。従来はパラメータがあるかどうかしか見ていなかった。FAPI に限らない
- **RSA1_5**：FAPI 1.0 Advanced（8.6.1）で、RSA1_5 で暗号化した Request Object を `invalid_request_object`、`id_token_encrypted_response_alg` / `authorization_encrypted_response_alg` が RSA1_5 のクライアントを `unauthorized_client` で拒否する
- **`client_id_alias`**：FAPI 1.0 Baseline の client identifier の不一致（5.2.2-19）の確認が、assertion の `iss` / `sub` をクライアント ID とだけ比べていたため、`client_id_alias` で認証するクライアントを拒否していた。この確認を削除し、汎用の検証（`iss` が `client_id` パラメータと一致、`sub` が `iss` と一致）に任せた（Issue #1921）
- **`x-fapi-interaction-id`**：UserInfo がリクエストの値（無ければ UUID）を返す（FAPI 1.0 Baseline 6.2.1-11）。リクエストで受け取った値は、アプリケーション API のログの MDC に `fapi_interaction_id` として出す（6.2.1-12）

### 7.1 影響を受ける構成 {#fapi-client-authentication-affected}

FAPI のスコープで PAR または refresh token を使うクライアントのうち、認可コードのトークンリクエストでは通らない認証をしているもの。認可コードのトークンリクエストで同じ要件をすでに満たしているクライアントは影響しない。

refresh token のリクエストのプロファイルは、その時点のテナントの `fapi_baseline_scopes` / `fapi_advance_scopes` / `fapi20_scopes` で決まる。これらの設定を変えると、発行済みの refresh token にも変更後のプロファイルの要件がかかる。

RSA1_5 を設定しているクライアントは次で確認できる。

```sql
-- PostgreSQL
SELECT tenant_id, id FROM client_configuration
WHERE payload->>'id_token_encrypted_response_alg' = 'RSA1_5'
   OR payload->>'authorization_encrypted_response_alg' = 'RSA1_5';

-- MySQL
SELECT tenant_id, id FROM client_configuration
WHERE JSON_UNQUOTE(JSON_EXTRACT(payload, '$.id_token_encrypted_response_alg')) = 'RSA1_5'
   OR JSON_UNQUOTE(JSON_EXTRACT(payload, '$.authorization_encrypted_response_alg')) = 'RSA1_5';
```

### 7.2 確認 {#fapi-client-authentication-check}

| ケース | テスト |
|---|---|
| FAPI 1.0 Baseline：refresh token で鍵長の要件、`client_id_alias` での認可コード・refresh token、UserInfo の `x-fapi-interaction-id` | `e2e/src/tests/spec/fapi_baseline.test.js` |
| FAPI 1.0 Advanced：PAR で RS256 の client assertion を拒否 | `e2e/src/tests/spec/fapi_advance.test.js` |
| FAPI 1.0 Advanced：RSA1_5 の拒否 | `FapiAdvanceVerifierRsa15Test`（ユニットテスト）|
| FAPI 2.0：refresh token で `aud` が issuer 以外の client assertion を拒否 | `e2e/src/tests/spec/fapi2_0_security_profile.test.js` |
| `client_assertion_type` の値 | `e2e/src/tests/spec/rfc7523_jwt_client_authentication.test.js` |
| 5.2.2-19 の不一致の検出（汎用の検証） | `e2e/src/tests/spec/fapi_baseline.test.js` / `fapi_ciba.test.js` |

## 9. 認可画面を別サイトに置く構成（Issue #1904 / PR #1905） {#cross-site-authorization-view}

**🟢 追加。** 認可画面を idp-server と別サイト（別の登録可能ドメイン）に置くと、認可画面からの XHR がサードパーティになり、Safari ではログインも OP セッションの保存も成立しなかった。別サイト認可画面モードを追加し、ブラウザの識別を Cookie から使い捨ての値 `auth_proof` に移し、認可フローの最後に idp-server を `/complete` でトップレベル遷移させるようにした。

### 9.1 影響 {#cross-site-authorization-view-impact}

- **既定は無効。** テナントの `ui_config.cross_site` またはクライアントの `extension.cross_site_authorization_view` を `true` にしない限り、挙動は変わらない
- **RP の実装は変わらない。** RP に届くコールバックは従来どおり
- **自作の認可画面は対応が要る**（有効にする場合のみ）。応答の `auth_proof` の保持、`authorize` への付与、`/complete` への遷移。手順は [認可画面を別サイトに置く](../content_05_how-to/phase-3-advanced/03-authorization-view-cross-site.md)
- **DB マイグレーションは無い。** 状態は既存の `authentication_transaction.attributes` に置く。トランザクションの更新で `attributes` も書くようになった

### 9.2 有効にする前に確認すること {#cross-site-authorization-view-check}

| 項目 | 必要なこと |
|---|---|
| 認可画面 | URL の fragment の `view_binding` を `x-view-binding` ヘッダーで送ることと、`auth_proof` に対応している（対応していない画面で有効にすると、認可画面からの呼び出しが 401、`authorize` が 400） |
| `session_config.cookie_same_site` | `Lax`（既定）または `None`。`Strict` では `/complete` が拒否される |
| 認証ポリシーの `auth_session_binding_required` | `true`（既定）にする。別サイト構成を動かすために `false` にしていた場合は、有効化のあとで戻す。`false` のままだと `view_binding` と `/complete` でのブラウザの束縛が外れる |
| `cors_config.allow_origins` | 認可画面のオリジンを含む |
| idp-server の前段（API Gateway / CDN / WAF） | `x-view-binding` ヘッダーを転送する。CORS のプリフライトに前段が応答する構成では、`Access-Control-Allow-Headers` にも含める（idp-server 側は設定不要で含める） |
| 切り替えの方法 | 使用中のクライアントで切り替えると、認証途中の利用者が一度だけ失敗する。別クライアントへの乗り換えかメンテナンスで切り替える |

## 10. リクエストオブジェクトの独自クレーム（Issue #1938 / PR #1937） {#request-object-custom-params}

リクエストオブジェクト（JAR）を使った認可リクエストで、カスタムパラメータが署名されていないクエリからだけ取られ、JWT の独自クレームは捨てられていた。RFC 9101 Section 4 のとおり、リクエストオブジェクトからも読むようにした。

| リクエストの形 | 修正前 | 修正後 |
|---|---|---|
| `request=` JWT | クエリだけ | JWT ＋ クエリ。同じキーは JWT（OIDC Core 6.3.3） |
| `request=` JWT（FAPI 1.0 Advanced） | クエリだけ | JWT だけ（FAPI 1.0 Advanced 5.2.2-10） |
| PAR | 本文（本文の JWT の独自クレームは捨てていた） | 本文 ＋ JWT |

- JWT の登録済みクレーム（`iss` / `sub` / `aud` / `exp` / `nbf` / `iat` / `jti`）と、OAuth / OIDC の既知パラメータは除く。数値と真偽値は文字列にし、オブジェクトと配列は取り込まない
- **🔴 FAPI 1.0 Advanced**：クエリだけで渡したカスタムパラメータは使われない。画面の振り分け（`ui_config.variant_param`、既定 `view_version`）をクエリで渡しているクライアントは、リクエストオブジェクトに入れる
- **🟡 リダイレクト URL**：リクエストオブジェクトの値は、認可画面へのリダイレクト URL に載せない（署名・暗号化して送られた値を、ブラウザの履歴や Referer、画面側のアクセスログに出さないため）。リクエストオブジェクトを含む PAR は、どの値がリクエストオブジェクトから来たか区別できないので、カスタムパラメータを URL に載せない。view-data の `custom_params` には、どの場合も載る。URL のクエリから読んでいる認可画面は、view-data から読むようにする
- 画面の振り分けの判定はサーバー側で全部の値を見るので、リクエストオブジェクトに入れた値でも振り分けは効く

## 11. 認可リクエストのカスタムパラメータとの照合（Issue #1907） {#custom-params-verification}

**🟢 追加。** RP が認可リクエストで渡した値（例：会員番号）と、ログインした利用者の属性を、認証ポリシーの条件式や属性照合の条件のステップで突き合わせられるようにした。

- 条件式から `$.request.custom_params.<名前>` で読める。右辺は `value_path` でコンテキストの path を指定できる（`eq` / `ne` のみ。どちらかの値が無いとき `eq` は false）
- 見えるのは、ポリシーの `custom_params_trusted_sources` に含まれる出どころの値だけ。既定は `pushed`（クライアント認証をした PAR）と `request_object`（署名されたリクエストオブジェクト）。クエリ、署名の無いリクエストオブジェクト、公開クライアントの PAR の値は `query` 扱いで、既定では見えない
- 出どころは認可エンドポイントで決め、認証トランザクションの `context.custom_params` に保存する（既存の JSON 列。マイグレーションは無い）
- 属性照合のステップ、または `$.request.*` / `$.attribute-verification.*` を見る条件を含むポリシーでは SSO しない。view-data の `session_enabled` が `false`、`authorize-with-session` は 400、`prompt=none` は `login_required`。照合は認可リクエストごとの確認で、セッションでは代わりにならないため（属性照合は v0.14.0 で追加したもので、既存の構成への影響は無い）

既存の設定には影響しない（新しい項目を書かない限り挙動は変わらない）。詳細は [認証ポリシー](../content_06_developer-guide/05-configuration/authentication-policy.md#request-custom-params)。

## 12. DPoP proof と Client Attestation PoP JWT のリプレイ検出（Issue #1893） {#jti-replay-detection}

DPoP proof（RFC 9449 Section 11.1）と `attest_jwt_client_auth` の Client Attestation PoP JWT（draft-ietf-oauth-attestation-based-client-auth Section 12.1）で、受け付けた `jti` を記録し、同じ JWT の 2 回目を拒否するようにした。

- **🟡 `iat` の許容範囲を ±60 秒に短縮**（従来は ±5 分）。テナントの `authorization_server.extension` で 1〜600 秒の範囲で変更できる（範囲外はテナントの作成・onboarding・認可サーバー設定の更新で 400）

  | 設定 | 既定 |
  |---|---|
  | `dpop_proof_acceptable_window_seconds` | `60` |
  | `client_attestation_pop_acceptable_window_seconds` | `60` |

- **🟡 同じ proof の 2 回目を拒否**。対象はトークンエンドポイント（各グラント）、PAR、userinfo、introspection、`/me` 系 API の DPoP 束縛の確認、ABCA のクライアント認証（トークン、PAR、CIBA、取り消し、introspection）。リクエストごとに新しい proof を作っているクライアントには影響しない
- 記録は Redis に置く（`SET NX EX`、`iat` の窓が閉じるまで）。キーはテナント・種類・鍵（DPoP は JWK Thumbprint、ABCA は client_id）・`jti` のハッシュ。DB のマイグレーションは無い
- Redis を設定していない配備（起動時に warn）と Redis のエラー時は記録せず、`iat` の窓だけで判定する
