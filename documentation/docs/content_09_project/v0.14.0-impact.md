## 1. セルフサービス連絡先の確認・変更 {#self-service-contact}

認証済みエンドユーザーが自分の**メールアドレス**または**電話番号**を確認・変更する API を追加した（#1876 / Issue #1416）。

```
POST /{tenant-id}/v1/me/{email|phone}/verification            スコープ openid
POST /{tenant-id}/v1/me/{email|phone}/verification/{id}/verify スコープ openid
POST /{tenant-id}/v1/me/{email|phone}/change                   スコープ {channel}:change
POST /{tenant-id}/v1/me/{email|phone}/change/{id}/verify        スコープ {channel}:change
```

詳細は [セルフサービス 連絡先の確認・変更](../content_06_developer-guide/05-configuration/contact-verification.md)。

### 1.1 DBマイグレーション {#db-migration}

**⚙️ 全環境で必須。**

| ファイル | 内容 |
|---|---|
| `libs/idp-server-database/postgresql/V0_14_0_1__contact_verification_challenge.sql` | `contact_verification_challenge` テーブル + index 2 本 + RLS |
| `libs/idp-server-database/mysql/V0_14_0_1__contact_verification_challenge.mysql.sql` | 同（MySQL に RLS は無いため `tenant_id` 述語のみ）|

新規テーブルの追加のみで、既存テーブルへの変更は無い。

### 1.2 変更用スコープ {#change-scope}

**🔒 要点検。** 確認（`/verification`）は `openid` で足りるが、**変更（`/change`）は専用スコープを要求する**。

```json
"scopes_supported": ["openid", "profile", "email", "email:change", "phone:change"]
```

テナントの `scopes_supported` とクライアントの `scope` の**両方**に追加する必要がある。クライアント登録スコープの allow-list フィルタが効くため、片方だけではトークンに載らず、変更エンドポイントが常に `403 insufficient_scope` になる（fail closed）。

分離した理由は、確認と変更で動くものが違うため。

| | 確認 | 変更 |
|---|---|---|
| 変わるもの | `*_verified` のみ | 値 +`*_verified`（+ 対応する identity policy なら `preferred_username`）|
| 送信先 | 現在値に**固定** | リクエストの `new_value` |

変更を `openid` で通すと、**第三者クライアントに発行した通常の OIDC トークンにも識別子の移動能力を与える**ことになる。

### 1.3 管理権限 {#admin-permission}

**🔒 要点検。** サポート照会用の管理API に `idp:contact-verification-challenge:read` を新設した。

```
GET /v1/management/tenants/{tenant-id}/contact-verification-challenges
GET /v1/management/tenants/{tenant-id}/contact-verification-challenges/{id}
GET /v1/management/organizations/{org-id}/tenants/{tenant-id}/contact-verification-challenges
GET /v1/management/organizations/{org-id}/tenants/{tenant-id}/contact-verification-challenges/{id}
```

権限照合は `PermissionMatcher` のワイルドカード方式なので、**`idp:*` を持つロール（既定の `administrator`）は自動的に含む**。影響を受けるのは権限を明示列挙しているロールだけで、その場合は追加が必要。

### 1.4 管理APIが有効な検証コードを返す {#management-verification-code}

**🔒 要点検。**

```json
{ "target_value": "...", "delivery": "internal", "verification_code": "123456", "attempts": 0, "expired": false }
```

「コードが届かない」という問い合わせに答えるための API なので、**実際の送信先と有効なコード**を返す。チャレンジの消費には本人のアクセストークンが要るため、コードだけを入手したオペレーターが単独で確定させることはできない。

監査ログは永続なので、`after` ペイロードからは `verification_code` と `external_reference` を落としている。

委譲構成（外部サービスがコードを生成する場合）は `delivery: "external"` になり、`verification_code` の代わりに `external_reference` を返す。

### 1.5 セキュリティイベント型の追加 {#security-events}

**🟢 追加。** 16 種増えた。

```
{email,phone}_{verify,change}_request_{success,failure}
{email,phone}_{verify,change}_{success,failure}
```

ログイン時の `email_verification_*` とは別物で、こちらは**意図的なプロフィール操作**を記録する。確認と変更を分けてあるのは、変更だけがログイン識別子を動かすため。

フック / SIEM 側でイベント型を allow-list している場合は追加が必要。

### 1.6 テナント設定に `contact_change_policy` が増えた {#contact-change-policy}

**🟡 挙動変更。** `identity_policy_config` に `contact_change_policy` が加わり、**テナント取得のレスポンスに常に含まれる**（未設定でも既定値が出る）。

```json
"identity_policy_config": {
  "identity_unique_key_type": "EMAIL_OR_EXTERNAL_USER_ID",
  "contact_change_policy": {
    "identifier_move": { "allowed": true, "notify_previous_value": true },
    "attribute_only":  { "allowed": true, "notify_previous_value": true }
  }
}
```

影響するのは 2 パターン。

- テナント設定のレスポンスを**厳密なスキーマで検証**している自動化 → 未知キーで落ちる可能性
- **GET → 編集 → PUT** を自分で書いている運用 → 既定値がそのまま保存されるようになる

既定で効くのは `notify_previous_value: true` のみで、**変更の重さは既定では規定されない**（スコープだけが門番）。識別子が動くテナントは `authentication_conditions` / `max_auth_age_seconds` を明示的に書くことを推奨する。

`allowed` が掛かるのは**変更だけ**で、確認（`/verification`）には掛からない。確認は値を置き換えず `*_verified` を立てるだけのため。`authentication_conditions` / `max_auth_age_seconds` は確認にも掛かる。

### 1.7 `delete-expired-data` の内訳 {#delete-expired-data}

**🟡 挙動変更。** `POST /v1/admin/operations/delete-expired-data` のレスポンスに `contact_verification_challenge` が加わった。

```json
{ "deleted": { "...": 0, "contact_verification_challenge": 47 }, "total_deleted": 47 }
```

期限切れチャレンジは他の有効期限付き 7 テーブルと同じ入口で回収される。件数を固定長で扱っている自動化は影響を受ける。

### 1.8 既存の認証設定への影響 {#authn-config}

**影響なし。** 送信には既存の `type: "email"` / `type: "sms"` 認証設定をそのまま流用するが、

- 追加した `resend_cooldown_seconds` を読むのはセルフサービス側だけで、ログイン OTP 側は `retry_count_limitation` / `expire_seconds` しか読まない
- `templates` の `{email,phone}_{verify,change}` / `*_notice` は**未定義ならそれぞれの既定にフォールバック**するため、既存テンプレートの変更は不要（ただし `*_notice` だけは**フォールバックせずスキップ**する。[理由](../content_06_developer-guide/05-configuration/contact-verification.md)）
- `details` は生の `Map` のまま往復するため、保存済み設定に影響しない

認証ポリシー（`flow` 設定）の追加も不要。
